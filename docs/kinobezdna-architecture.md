# Архитектура «Кинобездна» — To-Be

## 1. Обзор изменений (As-Is -> To-Be)

| Характеристика | As-Is (монолит) | To-Be (микросервисы) |
|---|---|---|
| Код | 1 репозиторий, 1 бинарь | 7 сервисов, независимые деплои |
| База данных | 1 PostgreSQL | 7 DB (one-per-service) |
| Интеграция | синхронные HTTP | REST + Kafka (events) |
| Точка входа | напрямую в API | API Gateway |
| Масштабирование | масштабирование всего | hot-spot сервисы масштабируются отдельно |
| Рекомендации | единственный асинхронный вызов | Recommendation Adapter + Kafka |
| Учёт девайсов | ? | device-aware routing в Gateway |

## 2. Разделение на домены

### User Service
- **Сущности:** пользователи, сессии, роли
- **Ответственность:** регистрация, логин, JWT, профили
- **База:** users_db

### Catalog Service
- **Сущности:** фильмы, видео, жанры, актёры, метаданные
- **Ответственность:** каталог контента, поиск, фильтрация
- **База:** catalog_db

### Rating Service
- **Сущности:** оценки (пользователь -> фильм)
- **Ответственность:** выставление оценки, расчёт средних, рейтинги
- **База:** ratings_db

### Favorites Service
- **Сущности:** папки избранного, элементы папок
- **Ответственность:** CRUD избранного, папки
- **База:** favorites_db

### Subscription Service
- **Сущности:** планы подписки, активные подписки пользователей
- **Ответственность:** управление подпиской, статусы, авто-продление
- **База:** subscriptions_db

### Payment Service
- **Сущности:** транзакции, методы оплаты, счета
- **Ответственность:** обработка платежей, биллинг
- **База:** payments_db

### Discount Service
- **Сущности:** промокоды, скидки, акции
- **Ответственность:** валидация промо, расчёт скидок
- **База:** discounts_db

### Recommendation Adapter
- **Сущности:** кэш рекомендаций
- **Ответственность:** прокси к сторонней RS, кэширование, подписка на события
- **База:** нет (stateless, кэш в памяти / Redis)

## 3. API Gateway

**Роль:** единственная точка входа для всех клиентов.

**Функции:**
- **SSL termination** — шифрование обрывается здесь
- **JWT validation** — проверка токенов аутентификации
- **Rate limiting** — ограничение запросов per user
- **Device-aware routing** — адаптация ответов по устройству:
  - Mobile: компактный JSON, только ключевые поля
  - Laptop: полный payload
  - TV: адаптированный payload + BFF-агрегация
- **Request aggregation** (BFF для TV) — один вызов от TV клиента
  собирает данные из нескольких сервисов

**Кандидаты:** Kong, NGINX Plus, AWS API Gateway, Apigee

## 4. Интеграционное взаимодействие

### Синхронное (REST / gRPC)
```
Клиент -> API Gateway -> Сервис -> DB -> ответ
```
Используется для:
- CRUD операций в реальном времени
- Аутентификация, выбор фильма, составление избранного
- Оплата, активация подписки

### Асинхронное (Kafka)
```
Сервис A -> publish event -> Kafka -> Сервис B (consume)
```
Сценарии:
- **rating.events** — пользователь оценил фильм
  - Recommendation Adapter обновляет модель
  - Favorites может предложить «похожее в избранное»
- **payment.events** — оплата прошла
  - Subscription обновляет статус подписки
- **user.events** — новый пользователь / изменение профиля
  - Recommendation инициализирует стартовый набор

## 5. Рекомендательная система

Вместо прямого вызова из монолита, введён **Recommendation Adapter**:

```
[Каталог] --REST--> [Rec Adapter] --HTTPS--> [Внешняя RS]
                                ^
[Kafka rating.events] ---------+
```

- Подписывается на события оценок через Kafka
- Периодически опрашивает внешнюю RS за подборками
- Кэширует результаты для быстрого ответа
- Внутренние сервисы вызывают только Adapter, не RS напрямую

## 6. Device-aware подход

Разные девайсы -> разные интерфейсы -> разное количество данных.

Решение: **API Gateway маршрутизирует с учётом устройства**:
- По `User-Agent` или custom header `X-Device-Type`
- Mobile: gateway запрашивает подмножество полей
- TV: gateway агрегирует несколько сервисов в один ответ (BFF)
- Laptop: полный ответ

Альтернатива: **GraphQL Gateway** — клиент запрашивает только нужные поля.

## 7. Стратегия миграции

Strangler Fig паттерн:

1. **Фаза 1:** Развернуть API Gateway перед монолитом
2. **Фаза 2:** Выделить User Service (аутентификация — самая понятная граница)
3. **Фаза 3:** Выделить Catalog Service (каталог — read-heavy, легко кэшировать)
4. **Фаза 4:** Выделить Payment + Subscription Service (критичная бизнес-логика)
5. **Фаза 5:** Rating + Favorites (низкий трафик, простая миграция)
6. **Фаза 6:** Discount Service + Recommendation Adapter
7. **Фаза 7:** Декомиссия монолита

## 8. Ключевые паттерны

| Паттерн | Где применяется |
|---|---|
| API Gateway | Единая точка входа |
| DB per Service | Изоляция данных |
| Event-Driven (Kafka) | Асинхронная интеграция |
| BFF (Backend for Frontend) | TV-клиент, агрегация |
| Strangler Fig | Поэтапная миграция |
| Adapter / Anti-Corruption | Recommendation Adapter |
| CQRS (опционально) | Catalog — чтение vs запись |
